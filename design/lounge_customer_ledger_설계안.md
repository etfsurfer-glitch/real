# 중개사 라운지 개편 — 고객 원장(요건·거래계획) 설계안

작성 2026-08-05. 참고 프로토타입(고객 원장 화면)을 바탕으로 한 **계획 문서**. 구현 전 합의용.

---

## 0. 왜 바꾸나

지금 라운지는 **기능별 탭 12개**가 나란히 있다(대시보드·매물장·계약캘린더·고객관리·계약관리·콕집요청·매물점검·홈페이지·상담신청·직원관리·정보수정·내 사무소).
중개사의 하루는 기능 단위로 흐르지 않는다. **"이 손님을 어디까지 진행시켰나"** 가 축이다.

- 지금: 고객은 `biz_customers` 에 이름·전화·주소·메모만 있는 **주소록**이다.
- 필요한 것: 한 고객이 가진 **여러 요건**(구함 2건 + 내놓음 1건)과, 각 요건이 **무엇에 막혀 있는지**.

참고 프로토타입이 정확히 이 문제를 푼다. 핵심 착상 두 가지를 가져온다.

1. **고객 1명 = 행 1개가 아니다.** 공통 정보(이름·연락처)는 한 번, 요건은 하위 행으로 정규화.
2. **거래는 선행 조건의 사슬이다.** 출발 기반(현재 자산·거주·자금) → 선행 조건(해결할 일) → 거래 목표(구함·내놓음).
   미해결 선행 조건 중 가장 급한 것이 **병목**이고, 거기서 **다음 액션**이 나온다.

---

## 1. 지금 있는 것 / 없는 것

| | 현재 | 판정 |
|---|---|---|
| 고객 | `biz_customers` (이름·전화·주소·메모, 계약서에서 dedupe 누적) | 재사용 |
| 계약 ↔ 고객 | `biz_contract_parties` (역할: 임대인·임차인·매도인·매수인) | 재사용 |
| 일정 | `biz_events` (계약·중도금·잔금·입주·만기) | 재사용 |
| 계약서 | `biz_contracts` (AI 파싱 19/19) | 재사용 |
| 요건 | **없음** | 신설 |
| 거래 계획(기반·선행조건·연결) | **없음** | 신설 |
| 매칭 | 없음 (매물 DB는 있음) | 신설 — **우리 강점** |

`koczip_requests`(콕집요청)는 이미 요건과 같은 모양이다 — 지역·유형·거래·평형·예산·메모.
**들어온 요청을 그대로 고객 원장의 요건으로 승격**시키면 입력 부담 없이 원장이 채워진다. 이게 우리만의 유입 경로다.

## 2. 데이터 모델 (신설 4개)

```
biz_needs            요건 — 고객이 구하거나 내놓은 것 1건
  id, user_id, realtor_id, customer_id
  kind        구함 | 내놓음
  trade       A1 매매 | B1 전세 | B2 월세
  role        주안 | 대안 | 보유          -- 주력인지 대안인지
  budget_min, budget_max                  -- 구함
  ask_price                               -- 내놓음
  sido, sigungu, dong, complex_no, address
  area_min, area_max                      -- ㎡ 저장, 평 표기(면적 표기 표준)
  status      탐색 | 비교 | 협상 | 계약 | 완료 | 보류
  move_date                               -- 희망 입주·잔금
  src_request_id                          -- 콕집요청에서 승격된 경우
  memo, created_at, updated_at

biz_plan_bases       출발 기반 — 지금 가진 것
  id, customer_id, kind(자산|거주|자금), label, amount, memo

biz_plan_conds       선행 조건 — 확인하거나 해결할 일
  id, customer_id, title
  status      미정 | 진행 | 완료
  gate        계약 전 | 잔금 전 | 입주 전    -- 언제까지 끝나야 하나
  amount, expected_date, memo

biz_plan_links       연결 (다대다)
  from_kind(base|cond), from_id, to_kind(cond|need), to_id
```

`biz_plan_links` 를 다대다로 두는 이유: 프로토타입에서도 선행 조건 2개가 목표 2개에 **교차로** 걸린다
(전세보증금 반환 → 매매·전세 양쪽, 대출 한도 → 양쪽). 1:N 으로 두면 그 그림을 못 그린다.

### 파생값 — 저장하지 않고 계산한다

- **병목** = `status != 완료` 인 선행 조건 중 `gate` 가 가장 이르고 `expected_date` 가 가장 빠른 것.
- **준비상태** = 걸린 선행 조건이 전부 완료면 `준비 완료`, 하나라도 남으면 `선행 진행`.
- **다음 액션** = 병목에서 파생. 초안은 규칙으로 만들고(예: `일정 미정` → "○○에게 날짜 확인"),
  중개사가 덮어쓸 수 있게 `biz_plan_conds.memo` 와 별개 필드로 둔다.

> 저장하면 반드시 어긋난다. 조건 상태를 바꿨는데 준비상태가 그대로면 화면을 못 믿게 된다.

## 3. 화면

### 3-1. 고객 원장 (새 탭 — 기존 `고객관리` 대체)

```
고객 원장                       [고객 N] [구하는 조건 N] [내놓은 물건 N]  [전체 연락처 →]
[검색: 고객·전화·지역·물건]   [전체][구함][양쪽][내놓음]            [정렬: 최근 연락]

고객 | 전화 | 유형 | 요건 | 거래 | 역할 | 예산 | 내놓은가 | 지역·물건 | 평형 | 매칭 | 준비상태 | 다음 액션
─────────────────────────────────────────────────────────────────────────────────
한구매 010-…  구함  구함1 매매 주안 24~27억  —  강동구·고덕동 32평↑ [2건] ●선행진행  임대인에게 …
                    구함2 전세 대안  9~13억  —  강동구        32평↑ [1건]
```

- 고객 셀은 요건 수만큼 **세로 병합**(rowspan). 공통 정보를 반복하지 않는다.
- 유형(구함·양쪽·내놓음)은 요건에서 **자동 계산** — 손으로 고르게 하면 실제와 어긋난다.
- 「매칭 N건」은 장식이 아니라 **실제 우리 DB 조회 결과**(§4).

### 3-2. 펼침 — 거래 계획

3단 플로우. 왼쪽 출발 기반 → 가운데 선행 조건 → 오른쪽 거래 목표, 사이는 곡선 연결.

- SVG 커넥터. 노드 위치를 잡고 베지어로 잇는다(라이브러리 없이, CSP 제약과 무관).
- 하단 고정 줄: `● 현재 병목 ○○ | 다음 액션 ○○` + 오늘 배지.
- 모바일에서는 곡선을 버리고 **세로 3단 스택**(기반 → 조건 → 목표)으로 접는다.
  곡선은 좁은 화면에서 읽히지 않는다.

### 3-3. 대시보드 (2026-08-05 배포 완료 — 이 개편의 0단계)

히어로+현황 왼쪽 / 일정 오른쪽 2단. 일정 패널은 주간·월간·연간 전환 + 아래 목록.
개편이 진행되면 오른쪽 열에 **오늘의 병목 목록**(고객별 다음 액션)이 일정 아래로 붙는다.

## 4. 우리만의 무기 — 매칭

CRM 자체는 누구나 만든다. 우리에겐 **전국 매물·실거래 DB** 가 뒤에 있다. 요건이 정규화되는 순간
매칭이 공짜로 나온다.

- **구함 요건 → 매물**: `지역 + 거래유형 + 예산 + 평형` 으로 (1) 우리 사무소 매물장, (2) 전국 매물,
  (3) 급매 엔진(실거래 평균 대비 할인) 순으로 조회. 「매칭 2건」의 실체.
- **내놓음 요건 → 시세**: 같은 단지·평형의 최근 실거래·현재 최저호가·광고 배율(매도 경쟁 강도).
  "가격 협의" 를 근거를 갖고 하게 된다.
- **가격 변동 감지**: 요건에 걸린 단지의 신고가·급매 등장 시 **다음 액션 자동 제안**
  ("고덕그라시움 84㎡ 급매 신규 — 한구매님께 브리핑").

이건 이미 있는 것들(`find_apartments`·`find_quick_deals`·매물장·웹푸시)의 재조합이다. 새로 만들 게 적다.

## 5. 캘린더 연동

- 선행 조건 `expected_date` → `biz_events` 에 자동 반영(`event_type=기타`, 출처 표시).
- 요건 `move_date`(희망 입주·잔금) → 같은 방식.
- 대시보드 일정 패널이 그대로 받는다. **캘린더를 따로 관리할 필요가 없어진다.**
- 주의: 자동 생성 일정은 원본이 바뀌면 따라 바뀌어야 한다 → `biz_events` 에 `src_kind/src_id` 추가.

## 6. 정보 구조(IA)

탭 12개 가로 나열은 한계다. 참고 프로토타입처럼 **좌측 레일 + 그룹**으로.

```
영업     고객 원장 · 콕집요청 · 상담신청
매물     매물장 · 매물점검
거래     계약관리 · 계약캘린더
사무소   홈페이지 · 직원관리 · 내 사무소 · 정보수정
```

대시보드는 레일 최상단 고정. 모바일(비즈앱)은 현재 그리드 홈을 이 그룹으로 재배치.

## 7. 단계

| 단계 | 내용 | 산출 |
|---|---|---|
| **0** | 대시보드 2단(현황+일정) | **완료 2026-08-05** |
| **1** | 테이블 4개 신설 + 요건 CRUD API + 고객 원장 읽기 화면 | 원장이 보인다 |
| **2** | 콕집요청 → 요건 승격, 계약서 파싱 → 고객·요건 자동 생성 | 입력 없이 채워진다 |
| **3** | 거래 계획 편집 + 3단 플로우 + 병목·다음 액션 계산 | 프로토타입 화면 완성 |
| **4** | 매칭 엔진 연결(§4) | 우리만 되는 것 |
| **5** | 캘린더 양방향 연동 + 병목 알림(웹푸시·비즈 브리핑) | 손 안 대도 굴러간다 |
| **6** | IA 개편(좌측 레일) | 12탭 정리 |

각 단계는 그 자체로 쓸모가 있어야 한다. 1단계만 나가도 "고객별 요건 목록"이라는 값은 선다.

## 8. 먼저 정해야 할 것

1. **개방 시점** — `/biz/*` 는 전부 관리자 가오픈이다. 법률 준수 메모상 **중개사 약관 동의 게이트가
   캘린더·고객원장 개방의 선행 조건**이다. 1단계를 만들되 개방은 게이트 뒤로 둘지, 게이트를 먼저 칠지.
2. **역할 용어** — `주안 / 대안 / 보유` 를 그대로 쓸지. 현장 용어와 맞는지 확인 필요.
3. **선행 조건 프리셋** — 전세보증금 반환·주담대 한도·기존 주택 매도·전입 가능일 등 상위 N개를
   버튼으로 제공하면 입력이 빨라진다. 실제로 자주 걸리는 항목 목록이 필요하다.
4. **고객 개인정보** — 요건에 지역·예산이 붙으면 민감도가 올라간다. 사무소 전용 격리는 그대로 두되,
   직원 계정의 열람 범위를 owner/staff 로 나눌지.
5. **범위** — 1~3단계까지 갈지, 매칭(4)까지 한 묶음으로 볼지. 4가 실제 차별점이라 여기까지 가야 의미가 있다.
