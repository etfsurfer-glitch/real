# 중개사 라운지 개편 — 엑셀형 고객 원장 설계안

작성 2026-08-05. 참고 프로토타입(고객 원장) + **엑셀 대체 전략**을 합친 계획 문서. 구현 전 합의용.

---

## 0. 전제를 바꾼다 — 우리 경쟁자는 CRM이 아니라 엑셀이다

중개사 대부분은 엑셀을 쓴다. "CRM이 없어서" 가 아니라 **엑셀이 실제로 잘 맞아서** 쓴다.
그걸 인정하지 않고 만든 CRM은 예쁘지만 안 쓰인다. 우리 라운지가 지금 그 상태다.

### 엑셀이 이기는 이유 (없애면 안 되는 것)

| | 엑셀 | 보통의 CRM |
|---|---|---|
| 입력 | 아무 칸에나 아무거나 친다 | 필수 항목·모달·유효성 검사 |
| 이동 | Tab·Enter·방향키, 손이 키보드를 안 떠남 | 마우스로 버튼 찾기 |
| 조망 | 한 화면에 50행이 보인다 | 카드 5개, 스크롤 |
| 대량 | 50행 붙여넣기 3초 | 한 건씩 등록 |
| 소유 | 파일이 내 것, 언제든 열림 | 남의 서버 |
| 신뢰 | 뭐가 들었는지 내가 안다 | 어디에 뭐가 저장됐는지 모름 |

### 엑셀이 지는 이유 (우리가 파고들 틈)

- **시트끼리 안 이어진다.** 손님 시트 / 매물 시트 / 일정 시트를 손으로 옮겨 적는다.
- **아무도 안 알려준다.** 잔금일이 내일이어도 파일은 가만히 있다.
- **시세가 늙는다.** 호가·실거래를 손으로 다시 적어야 한다.
- **중복이 쌓인다.** 같은 손님이 세 번 들어가 있다.
- **인수인계가 안 된다.** 직원이 나가면 파일도 나간다.
- **모바일에서 못 쓴다.** 현장에서 못 본다.
- **유출되면 끝이다.** 파일 하나에 고객 전화번호 300개.

### 그래서 목표 한 줄

> **엑셀처럼 치게 하고, 엑셀이 못 하는 열을 옆에 붙인다.**

전환 비용을 0으로 만들고(붙여넣기), 되돌아갈 길을 열어 두고(내보내기),
그 위에 **엑셀로는 절대 만들 수 없는 열**(매칭·시세·D-day·병목)을 놓는다.
"이 열 때문에 엑셀로 못 돌아가겠다" 가 되는 순간이 성공 지점이다.

## 1. 화면의 중심은 그리드다

기존 계획에서 원장 테이블은 '보기 좋은 표'였다. 이제 **편집 가능한 스프레드시트**가 된다.

### 1-1. 반드시 되어야 하는 것 (이게 안 되면 엑셀 사용자는 3분 만에 떠난다)

- **키보드 전용 조작** — 방향키 이동, `Tab`/`Shift+Tab` 좌우, `Enter` 확정 후 아래,
  `Shift+Enter` 위, `F2`·더블클릭 편집, `Esc` 취소, `Delete` 비우기
- **타이핑 즉시 편집** — 셀을 고른 상태에서 글자를 치면 바로 입력이 시작된다(엑셀 동작)
- **범위 선택** — `Shift+방향키`, 드래그. 하단 상태바에 `선택 12칸 · 합계 284억 · 평균 23.6억`
- **복사·붙여넣기** — 클립보드를 **TSV**로 주고받는다. 엑셀↔우리 그리드가 그대로 오간다
- **채우기 핸들** — 오른쪽 아래 모서리를 아래로 끌면 복제
- **되돌리기** — `Ctrl+Z` / `Ctrl+Shift+Z`. 셀 단위 로그 기반
- **열 고정·정렬·필터** — 고객·전화 두 열 고정, 헤더 클릭 정렬, 열별 필터
- **가상 스크롤** — 수천 행에서도 끊기지 않게

### 1-2. 한글 IME — 여기서 대부분의 그리드가 깨진다

한글 조합 중 `Enter`는 **조합 확정**이지 셀 이동이 아니다.
`compositionstart` ~ `compositionend` 구간에는 키 핸들러를 통째로 비활성화하고,
`compositionend` 이후의 `Enter`부터 이동으로 친다. **실기기(맥·윈도우·모바일) 실측 필수.**
이걸 놓치면 "이름 치다가 커서가 아래로 튄다" 가 되고, 그 순간 신뢰를 잃는다.

### 1-3. 구현 방식

직접 만들면 클립보드·가상스크롤·되돌리기까지 큰 작업이다. 라이브러리를 쓰되 셀 렌더러는 우리가 짠다.

- 후보: `react-data-grid`(MIT, DOM 기반, 우리 규모에 충분) / `glide-data-grid`(MIT, canvas, 더 빠름)
- **DOM 기반 권장** — IME·접근성·기존 CSS 토큰 재사용이 canvas보다 훨씬 쉽다
- **라우트 분할 필수** — 현재 메인 번들이 2.1MB다. 그리드는 라운지에서만 `lazy()` 로 불러온다

## 2. 붙여넣기 = 도입 장벽의 90%

중개사가 **지금 쓰는 엑셀을 그대로 붙여넣으면 원장이 채워져야** 한다. 이게 유일하게 중요한 첫 기능이다.

1. 엑셀에서 범위 복사 → 우리 그리드에 `Ctrl+V`
2. 헤더 자동 매핑 — `이름·성명·고객명` → 고객, `연락처·전화·핸드폰·HP` → 전화번호,
   `예산·금액·희망가` → 예산, `지역·동네·희망지역` → 지역 …
3. **매핑 확인 화면 1회** — 틀린 것만 드롭다운으로 고친다
4. 중복 감지 — 이름+전화가 같으면 "3건이 기존 고객과 겹칩니다. 합칠까요 / 새로 넣을까요"
5. 넣기

**함정**: 엑셀에서 전화번호를 숫자 서식으로 저장했으면 `01012345678` → `1012345678` 로 앞 0이
이미 날아가 있다. 붙여넣을 때 감지해서 `0`을 복원할지 물어야 한다(조용히 고치면 안 된다).

## 3. 자유 입력을 막지 않는다 — 원문 열 + 점진적 구조화

엑셀의 진짜 강점은 **아무거나 칠 수 있는 것**이다. 스키마를 강요하면 진다.

- 모든 요건 행에 **`원문` 열**을 둔다. `강동구 고덕동 84 24~27억 10월입주` 라고 그냥 친다.
- 시스템이 파싱해 **구조화 열을 제안**한다(지역·평형·예산·입주희망). 이미 있는 AI 파싱 재사용.
- 제안은 **연한 배경 + 점선 밑줄**로 표시. `Tab` 한 번이면 확정, 무시하면 원문만 남는다.
- 구조화가 안 돼도 **행은 살아 있다.** 검색·정렬은 원문으로도 된다.

> 강요하지 않으면 오히려 채워진다. 구조화된 행은 §4의 계산 열이 붙어 눈에 띄게 쓸모 있어지고,
> 그걸 본 사용자가 스스로 나머지를 채운다.

### 사용자 정의 열

엑셀 사용자는 자기 열을 만든다(`소개자`, `차량`, `애견동반`…).
`biz_needs.extra_json` 에 자유 키·값으로 저장하고, 사무소별 열 정의는 `biz_sheet_columns` 에 둔다.
EAV 테이블은 과하다 — 검색은 원문 열과 주요 구조화 열로 충분하다.

## 4. 계산 열 — 엑셀이 못 만드는 열

사용자 입력 열과 **시각적으로 구분**한다(연회색 배경, 자물쇠 아이콘, 편집 불가).
항상 최신이고, 손댈 필요가 없다.

| 계산 열 | 내용 | 근거 데이터 |
|---|---|---|
| **매칭** | 이 요건에 맞는 매물 N건 | 우리 매물장 → 전국 매물 → 급매 엔진 |
| **시세** | 같은 단지·평형 최근 실거래 / 현재 최저호가 | `transactions`, `listings_current` |
| **경쟁** | 같은 물건 광고 배율(매도 경쟁 강도) | 광고 vs 물건(Σ1/same_addr_cnt) |
| **D-day** | 다음 일정까지 남은 날 | `biz_events` |
| **준비상태** | 선행 조건 전부 완료 여부 | `biz_plan_conds` |
| **다음 액션** | 병목에서 파생한 할 일 | 규칙 + 중개사가 덮어쓰기 가능 |
| **최근 연락** | 마지막 통화·문자·상담 | `biz_call_events`, 상담리드 |

매칭 셀을 클릭하면 오른쪽 패널에 매물 목록이 뜬다. 거기서 바로 **콕집요청 제안**으로 연결된다.

---

## 5. 시트끼리 잇는다 — 엑셀이 못 하는 두 번째

탭 = 시트지만, 시트끼리 **참조**한다.

```
고객 ──┬── 요건 (구함·내놓음)  ── 매칭 → 매물
       ├── 일정 (계약·중도금·잔금·입주·만기)
       └── 계약 (계약서 파싱)
```

- 요건 시트의 `고객` 열은 고객 시트를 참조하는 드롭다운 — **오타로 중복이 생기지 않는다**
- 계약서를 올리면 고객·요건·일정이 **동시에** 생긴다. 세 시트에 옮겨 적을 일이 없다
- 콕집요청이 들어오면 요건 행으로 **승격**된다 (`biz_needs.src_request_id`)

## 6. 되돌아갈 길 — 내보내기

**언제든 xlsx/csv 로 전체 다운로드.** 화면 어딘가에 상시 노출한다.

"내 데이터가 갇힌다" 는 불안이 도입을 막는 가장 큰 심리 장벽이다.
나갈 문을 크게 열어 두면 오히려 들어온다. 실제로 나가는 사람은 거의 없다.

## 7. 데이터 모델

기존 계획(요건·거래계획) 위에 그리드용을 얹는다.

```
biz_needs            요건 — 그리드의 한 행
  id, user_id, realtor_id, customer_id
  kind        구함 | 내놓음
  trade       A1 매매 | B1 전세 | B2 월세
  role        주안 | 대안 | 보유
  budget_min, budget_max          -- 구함
  ask_price                       -- 내놓음
  sido, sigungu, dong, complex_no, address
  area_min, area_max              -- ㎡ 저장, 평 표기(면적 표기 표준)
  status      탐색 | 비교 | 협상 | 계약 | 완료 | 보류
  move_date
  raw_text                        -- ★ 원문(자유 입력)
  extra_json                      -- ★ 사용자 정의 열
  src_request_id                  -- 콕집요청에서 승격
  sort_key                        -- 사용자 행 순서(엑셀처럼 끌어 옮김)
  memo, created_at, updated_at

biz_plan_bases       출발 기반   id, customer_id, kind(자산|거주|자금), label, amount, memo
biz_plan_conds       선행 조건   id, customer_id, title, status(미정|진행|완료),
                                 gate(계약 전|잔금 전|입주 전), amount, expected_date, memo
biz_plan_links       연결(다대다) from_kind(base|cond), from_id, to_kind(cond|need), to_id

biz_sheet_columns    사무소별 열 정의  realtor_id, key, label, type, width, order, hidden
biz_cell_log         셀 변경 이력      table, row_id, col, before, after, user_id, at
                                       -- 되돌리기 + 직원 여러 명일 때 "누가 바꿨나"
```

`biz_plan_links` 를 다대다로 두는 이유: 프로토타입에서도 선행 조건 2개가 목표 2개에 **교차로** 걸린다
(전세보증금 반환 → 매매·전세 양쪽, 대출 한도 → 양쪽). 1:N 이면 그 그림을 못 그린다.

### 파생값은 저장하지 않는다

병목 = 미완료 선행 조건 중 `gate` 가 이르고 `expected_date` 가 빠른 것.
준비상태·다음 액션도 여기서 계산한다.
**저장하면 반드시 어긋난다** — 조건을 바꿨는데 상태가 그대로면 화면 전체를 못 믿게 된다.

### 저장 방식

- 셀 편집 → 즉시 `PATCH` (낙관적 반영, 실패 시 셀에 빨간 테두리 + 재시도 큐)
- 동시 편집 충돌은 **last-write-wins + 변경 표시**. 실시간 동시편집(CRDT)은 이 규모에 과하다
- 오프라인 편집은 범위 밖. 다만 저장 실패가 조용히 삼켜지면 안 된다

## 8. 뷰 전환 — 같은 데이터, 네 가지 얼굴

기본은 **그리드**. 필요할 때만 바꾼다.

| 뷰 | 쓰는 순간 |
|---|---|
| **그리드**(기본) | 전체 훑기, 대량 입력·수정 |
| **원장 펼침** | 한 고객의 거래 계획(출발 기반 → 선행 조건 → 거래 목표) 곡선 플로우 |
| **캘린더** | 이번 주 잔금·입주 |
| **보드** | 상태별(탐색→비교→협상→계약) 파이프라인 |

거래 계획 플로우는 SVG 커넥터로 그린다. 모바일에서는 곡선을 버리고 **세로 3단 스택**으로 접는다.

---

## 9. 모바일 — 그리드를 억지로 넣지 않는다

스프레드시트는 좁은 화면에서 쓸 수 없다. 데이터는 같되 화면을 바꾼다.

- **카드 목록 + 한 줄 빠른 입력** (현장에서 손님 전화받으며 치는 용도)
- 통화 감지(설계된 사이드카)와 붙으면 **통화 종료 직후 "이 번호를 고객으로 저장할까요"**
- 오늘의 병목·D-day 만 추려 보여준다

## 10. 정보 구조(IA)

탭 12개 가로 나열은 한계다. 좌측 레일 + 그룹으로.

```
영업     고객 원장(그리드) · 콕집요청 · 상담신청
매물     매물장 · 매물점검
거래     계약관리 · 계약캘린더
사무소   홈페이지 · 직원관리 · 내 사무소 · 정보수정
```

대시보드는 레일 최상단 고정. 비즈앱(모바일)은 현재 그리드 홈을 이 그룹으로 재배치.

## 11. 단계 — 각 단계가 그 자체로 쓸모 있어야 한다

| 단계 | 내용 | 이 단계만으로 얻는 것 |
|---|---|---|
| **0** | 대시보드 2단(현황+일정) | **완료 2026-08-05** |
| **1** | `biz_needs` + 그리드 **읽기 전용** (고객·요건 시트, 열 고정·정렬·필터) | 고객별 요건이 한 화면에 보인다 |
| **2** | **셀 편집 + 키보드 + IME + 붙여넣기 + 내보내기** | **엑셀에서 이사 온다** ← 진짜 1차 가치 |
| **3** | 계산 열(매칭·시세·D-day·최근 연락) | 엑셀로 못 돌아간다 |
| **4** | 원문 열 AI 파싱 제안 + 사용자 정의 열 | 입력이 빨라진다 |
| **5** | 거래 계획(펼침 뷰) + 병목·다음 액션 | 프로토타입 화면 완성 |
| **6** | 캘린더 양방향 + 병목 알림(웹푸시·비즈 브리핑) | 손 안 대도 굴러간다 |
| **7** | 보드 뷰 · 모바일 카드 · IA 좌측 레일 | 마무리 |

**2단계가 승부처다.** 1단계는 준비, 3단계는 잠금(lock-in).
2단계 없이 3단계로 뛰면 "예쁜데 입력을 못 하는" 지금 상태가 반복된다.

## 12. 위험과 함정

| 위험 | 대응 |
|---|---|
| 한글 IME에서 커서가 튄다 | `composition` 구간 키 핸들러 차단, 실기기 3종 실측 |
| 전화번호 앞 0 소실 | 붙여넣기 시 감지 후 **물어보고** 복원(조용히 고치지 않는다) |
| 번들 비대 | 그리드는 라운지 라우트에서만 `lazy()` |
| 개인정보 노출 | 한 화면에 전화번호 수백 개 — 직원 권한(owner/staff) 분리, 열람 로그, 마스킹 토글 |
| 저장 실패를 모른 채 계속 입력 | 실패 셀 빨간 테두리 + 상단 배너 + 재시도 큐 |
| 동시 편집 충돌 | last-write-wins + "○○님이 방금 바꿨습니다" 표시 |
| 만들어도 안 쓴다 | 2단계 완료 시점에 **실제 중개사 3명에게 자기 엑셀을 붙여넣게 해보고** 결정 |

## 13. 먼저 정해야 할 것

1. **개방 시점** — `/biz/*` 는 전부 관리자 가오픈이다. 법률 준수 메모상 **중개사 약관 동의 게이트가
   캘린더·고객원장 개방의 선행 조건**이다. 만들되 게이트 뒤에 둘지, 게이트를 먼저 칠지.
2. **실제 엑셀 확보** — 중개사들이 지금 쓰는 엑셀 파일 5~10개를 봐야 열 매핑 사전을 만든다.
   이게 없으면 2단계 자동 매핑이 추측이 된다. **가장 먼저 필요한 것.**
3. **역할 용어** — `주안 / 대안 / 보유` 를 현장 용어 그대로 쓸지.
4. **선행 조건 프리셋** — 전세보증금 반환·주담대 한도·기존 주택 매도·전입 가능일 등.
   실제로 자주 걸리는 항목 목록이 필요하다.
5. **범위** — 3단계까지를 1차로 볼지, 5단계(거래 계획)까지 한 묶음으로 볼지.
