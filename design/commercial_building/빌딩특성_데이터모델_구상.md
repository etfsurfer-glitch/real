# 상업용 빌딩 특성 데이터 — 정리 구상

작성 2026-10-19. 사용자가 그동안 모아 온 "상업용 빌딩의 특성" 자료를 어디에, 어떤 모양으로
담을지 정하기 위한 설계안. 입지(상권) 분석인 `design/academy_commercial/상업용_입지분석_계획서.md`
와는 **대상이 다르다** — 그건 '어느 동이 좋은가'(지역 축), 이건 '이 건물은 어떤 건물인가'(건물 축)다.

## 0. 전제

사용자 드라이브 폴더(`18YX1sCVF6KG4mdMhMBMkpT6tNUz3SK6w`)는 현재 연동 계정으로 열리지 않아
**실제 컬럼 목록을 보지 못한 상태**로 쓴 구상이다. 아래 L4(정성 특성)의 항목은 예시이고,
자료를 확인하면 그 자리에 실제 항목이 들어간다. L0~L3과 뼈대는 자료와 무관하게 유효하다.

## 1. 첫 번째 결정 — 기준 엔티티는 '동'이고, 키는 지번이다

상업용 빌딩 데이터의 난이도는 전부 **"이 빌딩이 그 빌딩인가"**에서 온다. 계층을 먼저 못 박는다.

```
필지(토지)  ──┬── 건물(동) ──┬── 층 ──┬── 호
  PNU 19자리  │   ★ 기준 엔티티 │        │
  공시지가·용도지역│   연면적·층수·준공  │ 주용도  │ 임대료·임차인·공실
```

- **기준 = 건물(동)**. 상업용 빌딩의 '특성'은 대부분 동 단위에 붙는다(준공·층수·승강기·주차·구조).
- **1차 키 = 법정동코드(10) + 본번(4) + 부번(4) + 동일지번 내 일련번호**.
  대장 관리번호(`mgmBldrgstPk`)가 정본이지만 **조회를 해야 나온다** — 우리가 가진 모든 입력
  (네이버 매물, 국토부 실거래, 사용자 수집자료)은 주소/지번 기반이다. 그래서 지번을 조회 키로,
  대장 관리번호를 확정 키로 둔다.
- 반드시 깨지는 지점 3곳: ①한 지번에 여러 동 ②집합건물(구분소유)은 한 동에 호수가 수백
  ③한 건물이 여러 필지에 걸침. ①은 일련번호로, ②는 호 테이블로, ③은 대표필지+부속필지 목록으로.
- **임대료·공실·임차인은 동이 아니라 '호'에서 발생한다.** 사용자 자료가 동 단위인지 호 단위인지가
  정리 방식의 첫 갈림길이다(자료 확인 후 확정).

## 2. 두 번째 결정 — 특성을 5개 층으로 쪼갠다

한 테이블에 다 넣으면 안 된다. 출처가 다르고, 갱신 주기가 다르고, **믿을 수 있는 정도가 다르다**.

| 층 | 담는 것 | 출처 | 갱신 | 신뢰 |
|---|---|---|---|---|
| **L0 식별** | 지번·도로명·좌표·대장키·대표필지 | 대장 + VWorld 지오코더 | 거의 불변 | 정본 |
| **L1 공부 스펙** | 연면적·대지·건축면적·용적률·건폐율·지상/지하층수·높이·구조·지붕·주용도·사용승인·허가·착공·승강기·주차·내진·호수 | 건축HUB 표제부 | 연 1회 | 정본 |
| **L2 토지·규제** | 용도지역·지목·개별공시지가·접도 | VWorld | 연 1회 | 정본 |
| **L3 시장** | 매매 실거래·임대 호가·환산보증금·관리비·광고 체류일·추정 수익률 | nrg 실거래 + 광고 시계열 | 일별 | **추정** |
| **L4 운영·정성** | 임차인 구성·공실·엘리베이터 유형·주차 방식·냉난방·리모델링 이력·관리 상태·역 도보분·코너/대로변·층고·전면 길이 | **사용자 수집자료** + 광고 본문 | 수동 | 혼재 |

**이 표가 이번 일의 요지다.** L0~L3은 자동으로 채울 수 있고 이미 상당 부분 채워져 있다.
**L4는 자동으로 못 채운다 — 그게 사용자가 모아 온 자료이고, 그래서 그 자료가 해자다.**
단, L4는 L0 식별자에 붙지 못하면 영구히 쓸 수 없다. 적재 파이프라인(§6)이 그 일을 한다.

재수집 비용 추정: 694만 동 ÷ 100(numOfRows) ≈ **6.9만 콜**. 키당 1만/일, 건축HUB 승인된 키
2개로 1.8만/일 → **약 4일**. 상업용만 고를 수는 없다(API가 법정동 단위 전수 응답) — 대신
주거 표제부도 같이 들어와 확인설명서·단지 상세에 재사용된다.

> 선행 확인 필요: 메모리 기준 KEY4/5/6은 건축HUB 미승인, KEY7은 KEY1과 중복. 실제 승인 키 수에

## 4. 세 번째 결정 — 값마다 출처를 붙인다

사용자 수집자료는 수동·비정형이라 **공부와 충돌한다**(대장 연면적 1,200㎡ vs 실사 메모 "약 350평").
값을 덮어쓰면 어느 쪽이 맞는지 영구히 알 수 없게 된다. 그래서:

```sql
-- 긴 테이블: 값 1개 = 1행
building_attr(bld_key, field, value_num, value_txt, unit,
              source,        -- ledger | vworld | nrg | listing | user_sheet | user_photo
              source_ref,    -- 파일명·행번호·article_no·deal_id
              observed_on,   -- 그 값이 사실이었던 날
              confidence)    -- 1 정본 / 2 실사 / 3 광고문구 / 4 추정
-- 조회는 와이드 뷰로: 필드별 confidence 최솟값·observed_on 최댓값 1건 선택
```

충돌 우선순위: **대장 > 사용자 실사 > 광고 문구 > 추정**. 단 공실·임차인·관리비처럼
대장에 없는 필드는 사용자 실사가 정본이다.

## 5. 네 번째 결정 — 별도 DB

메인 `naverreal.sqlite`는 28.5GB로 루트 디스크가 이미 빠듯하다([[naverreal-disk-full-incident]]).
비단지 4DB 격리 원칙과 같이 **`/opt/koczip/data/buildings.sqlite`** 신규.

```
buildings          -- L0+L1 와이드(동 1행). bld_key PK, pnu, mgm_pk, 좌표, 24개 공부 필드
building_floor     -- 층별개요(이미 ledger_cache CD* 로 받는 포맷 그대로)
building_unit      -- 호(집합건물·임대차 단위). 임대료·공실·임차인은 여기
building_attr      -- §4 긴 테이블(L2·L3·L4 전부)
building_deal      -- 매각 이력(nrg 실거래 + 사용자 자료의 과거 거래)
staging_user_rows  -- 사용자 자료 원본 그대로(§6)
unmatched          -- 주소 매칭 실패분. 버리지 않는다
```

## 6. 사용자 자료 적재 파이프라인

```
① staging   원본 파일 → staging_user_rows (컬럼명·값 그대로, 1행 1건, 파일명+행번호 보존)
② normalize 컬럼 매핑표(수동 1회) → 표준 필드명·단위 변환(평→㎡, 억→원)
③ match     주소/건물명 → 지번 → bld_key
              a. 도로명·지번 주소 → VWorld 지오코더 → PNU
              b. 건물명 + 동 → title_cache 역검색(694만 동에서 bldNm 일치)
              c. 좌표만 있으면 coord_addr.sqlite 역지오코딩(이미 51.6만 캐시)
            ★ 유일해만 채택. 후보 2개 이상이면 unmatched 로 보류 — 오귀속 0 원칙
              ([[naverreal-regno-linking-safety]], [[naverreal-ledger-jibun-recover]]와 같은 규칙)
④ merge     building_attr 에 source='user_sheet' 로 적재(덮어쓰지 않는다)
⑤ report    매칭률·충돌 목록·unmatched 를 사람이 보는 표로
```
②의 매핑표가 사람이 한 번 손으로 만드는 유일한 부분이다. 자료를 보면 그 자리에서 만든다.

## 7. 단계

- **P0 — 자료 실사(0.5일)**: 드라이브 자료 확인 → 레벨(동/호)·식별자(주소/건물명/좌표)·
  L4 실제 항목 목록 확정 → 매핑표 초안. **이것 없이 스키마를 못 박으면 두 번 짠다.**
- **P1 — 골격 + 적재(1~2일)**: `buildings.sqlite` 생성, title_cache 694만 동을 L0+L1(7필드)로
  펌프 → 사용자 자료 ②~⑤ 적재 → 매칭률 보고.
- **P2 — 공부 스펙 전수(4~8일, 무인)**: 표제부 24필드 전국 재수집 배치(`title_full_ref` 재사용,
  재개형·쿼터 가드). 끝나면 L1 완성.
- **P3 — 시장 축 결합(1일)**: nrg 실거래·상가/사무실/빌딩 광고를 bld_key에 붙여 L3.
- **P4 — 노출**: 실거래지도 핀 상세([[naverreal-txmap-ledger]])가 이미 표제부를 보여 준다 →
  같은 자리에 L4를 얹는 것이 가장 싼 노출 경로.

## 8. 리스크

1. **매칭률이 전부다.** 사용자 자료에 지번이 없고 건물명만 있으면 매칭률이 급락한다(동명이 흔하다 —
   '○○빌딩'은 전국에 수십 개). P0에서 가장 먼저 볼 것.
2. **694만 동 중 상업용 130만의 '정확한' 경계가 없다.** 주용도는 동 대표값이고, 실제로는 1층 상가 +
   상층 주택이 섞인다(§샘플: 세차장+사무소+단독주택 한 동). 층별개요로 봐야 하고, 그러면
   '상업용 빌딩'의 정의 자체가 판단이 된다 — 정의를 문서에 고정해 두고 쓸 것.
3. **L3 수익률은 추정이다.** 상업 임대차는 신고의무가 없다(매매만 실거래). 호가÷실거래라
   면적 기준이 어긋난다 — 기존 `yield_est`와 같은 '참고' 라벨 유지.
4. **4일짜리 배치의 쿼터.** 건축HUB 승인 키 수를 먼저 확인. 다른 일일 수집(step 5e 등)과
   쿼터를 나눠 쓰므로 예산 분리 필요.
